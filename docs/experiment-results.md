# 實驗結果與可信度：從模型比較到數值驗證

> [!IMPORTANT]
> 本專案的重要成果不只有最高分，而是發現不合理數值後，保留紀錄、建立對照並限制結論。**Inception 在目前 TensorFlow／Metal 組合出現可重現異常，全部 Inception 結果暫停採信、不納入網站比較。其他模型局部抽查通過，不代表已全面驗證。**

## 1. 研究問題與實驗條件

原目標是比較十種 CNN 學習實作，在相同六類動物資料、RGB 160×160、Batch 32、Seed 42 下，改變三種學習率（0.00001／0.0001／0.001）與四種優化器（Adam／SGD／AdamW／RMSprop）。每組固定十輪，以驗證 Accuracy 最高的權重產生分類報告；測試集留到最後。

模型保留各自特色，並非逐點重現論文；差異見 [架構說明](model-differences.md)。所有組合使用相同數值並不代表每個模型都達到最佳能力。各優化器的附加設定也不同，實驗比較的是整組配方，詳見 [優化器筆記](optimizers.md)。

- 資料：train 19,626／validation 2,453／test 2,452 張。已依檔案、像素與已知同源群組去重，不保證排除所有近似圖。
- 開發與 Metal 訓練：Apple M2 Max，TensorFlow 2.15.0、Keras 2.15.0、tensorflow-metal 1.1.0，Python 3.11、float32。
- CPU／Metal 固定重播使用同一個套件環境，只在 CPU 對照隱藏 GPU；模型、初始權重檔、已增強的輸入圖片與標籤完全共用。
- 歷史耗時含部分休眠、人工暫停及散熱條件變化，不作速度排名。部分早期成績使用 CPU，介面保留環境標示。

## 3. 問題怎麼被發現

最初兩組 Inception＋Adam 在第一輪提早停止，Loss／指標出現 NaN／Inf。重試後仍發生異常，且有回報為負的 Top-3 或超過 100% 的 Accuracy。

```text
Accuracy = 答對張數 / 總張數
```

這個比例必須介於 0 與 1。負值不是學得不好，也不是可接受的正常四捨五入差異。NaN 代表非數值；Loss 停住、猜同一類本身則不足以判定軟體錯誤，也可能是欠擬合或參數不合適。

初次只檢查有限值與輪次，會漏掉「數字有限，但範圍不合理」的情況。因此後續擴查逐輪 CSV 與批次 console，保留原紀錄並另做診斷，不刪掉失敗或把它改成成功。

## 4. 對照驗證：控制了什麼，實際看到什麼

### 固定初始權重與輸入重播

先用 CPU 建立一份初始權重；將 64 批已增強訓練圖片（每批 32 張）與標籤保存並計算 SHA-256。每個對照子程序重新建立模型、載入同一權重，按同一批次順序執行。CPU 與 Metal 各測兩個學習率，沒有讀取測試集。

| Adam 學習率 | CPU | Metal |
|---|---|---|
| 0.0001 | 64／64 批正常，檢查點未見非有限權重 | 第 31 批 Accuracy 回報約 −0.2692，提前停止 |
| 0.00001 | 64／64 批正常，檢查點未見非有限權重 | 第 3 批 Accuracy 回報約 −0.3460，提前停止 |

**更細的線索：**0.0001 的 Metal 短測停止後，讀回準確率累積值為 347／992（約 34.98%），卻與當批回報的負值不一致；0.00001 的累積值為 22／96（約 22.92%），也與回報不一致。固定重播當下的權重仍是有限值，抽樣推論也為有限值。

這表示不能把所有負準確率都直接解釋成「權重已壞掉」或「梯度爆炸」。指標回傳張量、同步、圖最佳化與底層實作之間的互動都值得追查。另一次使用即時讀圖增強的 Metal 短測，曾讀到首層權重與 Adam 狀態的非有限值，因此也不能把問題只當成 UI 顯示。

### 其他模型的 CPU 獨立核對

九種非 Inception 模型各挑出驗證 Accuracy 最高、已完成十輪且有完整報告的一份權重；每類取保存報告排序中的前十張驗證圖，共六十張。CPU 載入權重後，獨立以 argmax 與正確標籤計算 Accuracy，核對原報告的逐張分類。

- 九份權重未發現 NaN／Inf，輸出機率通過基本範圍與加總檢查。
- 540／540 次 CPU 分類結果與原 Metal 報告一致。
- 這是固定的分層抽查，**不是隨機代表性樣本、不是九模型的所有十二種設定，也不是完整驗證集重算**。
- 一致的是分類答案，不宣稱每一個機率小數完全相同。抽樣準確率不得與完整驗證準確率直接比大小。

匿名機器可讀紀錄：[verification.json](../results/verification.json)。只提供數值、條件與雜湊；不公開照片、權重、個人路徑或逐圖檔名。

## 5. 問題原因推測：證據與不確定性

| 推測 | 目前證據與判斷 |
|---|---|
| 學習率太小，所以 Loss 不降就變 NaN | 不支持這個說法；太小通常學得慢，不能解釋負準確率；同兩種學習率的 CPU 短測正常 |
| 圖片或標籤有 NaN／Inf | 已快取批次的基本數值檢查正常，同批 CPU 通過；不能據此宣稱整個資料集完全沒問題 |
| 混合精度 FP16 溢位 | 正式程式未開啟混合精度，檢查為 float32；不支持直接把它歸因於半精度 |
| 一定是 Adam 演算法錯 | 不支持；換 legacy Adam 的隔離短測仍有異常，歷史 Inception 其他優化器也有不合理回報 |
| 此 TensorFlow／Metal 組合的特定執行路徑 | 控制輸入後 CPU 正常、Metal 可重現，強烈支持後端相依問題；但尚未定位到算子、外掛版本或驅動中的哪個部分 |
| 因為機器發熱或休眠才發生 | 沒有足夠證據；歷史中斷會影響耗時，但不能直接解釋這次固定重播的數值異常 |

本專案使用 **TensorFlow／tensorflow-metal**，不是 PyTorch 的 `device="mps"`。`torch.autocast`、`PYTORCH_ENABLE_MPS_FALLBACK` 與 `torch.autograd` 不能直接修復這份程式。也沒有足夠證據稱為已確認的某個「著名 bug」。

## 6. 解決方案：現在採取與尚未採取

**已採取：**

1. 保留全部訓練與失敗紀錄；展示將所有 Inception 隔離為待查，沒有刪掉或補上假的零分。
2. 固定初始權重和輸入，做 CPU／Metal 重播；用 CPU 獨立核對其他模型的部分預測。
3. 匯出快照增加指標範圍、非有限值、張數與混淆矩陣一致性檢查。這些是必要檢查，不能保證全面正確。
4. 對外保留執行環境與驗證範圍；不把程式完成、裝置矩陣測試或沒有例外視為模型驗證通過。

**尚未直接套用的選項：**

- 調低學習率、加梯度裁剪、換優化器／BN／模型架構：會改變比較條件，且目前未證實能修好，所以不為了取得分數直接改正式模型。
- 升級或更換 TensorFlow／外掛：可在獨立環境做相同重播，必須留下版本與結果，不覆蓋原環境。
- 改用 CPU 訓練 Inception：可能避開受影響路徑，但仍須先做更長對照；完整結果應另成 CPU 系列，不能假裝填進原 Metal 排名。
- NVIDIA Docker：提供待驗證設定，尚未實機建置／訓練，不宣稱換硬體即可修復。

## 7. 觀點與 QA：實驗過程提出的問題

### CPU 跟 GPU 訓練會得到完全相同的權重嗎？差很多嗎？

不保證。浮點數加總順序、運算實作與隨機運算可能不同，小差異經訓練更新可能累積；沒有通用的「最多差幾 %」。權重數值不同也不代表能力一定差很多。正常差異不包含負準確率。若載入同一權重只做 CPU 推論，權重不會因此被重新訓練。

### CPU 就不會有梯度問題嗎？

CPU 一樣算梯度，也可能溢位或發散。本次只證明兩個設定各 64 批對照正常，不保證完整十輪或所有優化器正常。改 CPU 是替換底層實作，不是停止計算梯度。

### 沒報錯、Loss 有下降，模型就沒問題嗎？

不是。Loss 停住可能是欠擬合；Loss 下降也可能掩蓋其他問題。應同時看數值範圍、實際輸出、獨立重算與重現對照。生成圖像看起來正常或只試幾題，也不能證明所有運算正確。

### 模型公司公布的指標可以相信嗎？為什麼還測數學題、繪圖？

指標是指定條件下的證據，不是無條件保證。任務與數值並不對立：一百題數學答對九十題，就是 Accuracy 90%。任務評測是要測實際能力，並非只是補救硬體浮點差異；訓練 Loss 不能單獨代表數學推理或繪畫品質。要看題目、是否有資料洩漏、提示詞、工具／計算預算、評分方式、樣本量與外部重現。這次作品也遵守相同原則，公開限制而非只公開最高分。

### RMSprop 比 SGD／AdamW 快，代表它比較好嗎？

速度與分類能力是不同問題。歷史同模型同學習率的 Metal 紀錄，某些模型的 RMSprop 確實較快，但本專案 SGD／AdamW 有權重衰減，另有 Metal 實作、模型結構、散熱與暫停因素。沒有做固定批次的專門效能對照前，不把速度差歸因於單一原因。網站每三秒抓一次進度、後端每十批回報，跳很多批也不等於一秒算完。

### 風扇轉就過熱嗎？為什麼每組休息？

風扇是正常散熱，不能由聲音推算溫度。熱壓力 nominal／fair／serious／critical 是系統狀態，不是攝氏溫度。休息是保守的操作策略；不能用機身手感或熱壓力 0 證明數值運算正確，也不能因異常就認定硬體已損壞。

### 為什麼選擇保留空缺，不把兩組 CPU 跑滿就補進去？

因為疑點不限於那兩組失敗，其他已完成 Inception 也有不合理回報。混入 CPU 成績不能修復既有 Metal 比較；因此保留十二組的狀態，先隔離整個 Inception 系列。

## 8. 結論與後續

**結論：**這份作品展示模型學習與實驗驗證能力，而非宣稱找出最強模型。九種非 Inception 模型局部抽查通過，保留探索結果；Inception 的後端相依異常可重現，具體根因仍未定案。

**後續依序：**

1. 針對最佳候選權重，做完整驗證集 CPU 重算，保存與原報告的差異；先不動測試集。
2. 在 Inception 重播中逐步縮小指標回傳、圖最佳化及相關算子；必要時使用 TensorFlow 的數值檢查工具。儀器化可能改變執行時序，要和原始短測分開記錄。
3. 在獨立版本與 NVIDIA 環境重播；若要補 CPU 訓練，建立新系列並標示條件差異。
4. 最佳設定多 seed 重跑，報告平均與離散程度，再執行一次保留測試集評分。
5. 更新網站快照與驗證狀態；Docker 完成實測後才移除待驗證標記。
